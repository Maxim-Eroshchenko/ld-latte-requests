# LD LATTE · Заявки на автоматизацию

Внутренний сервис на React, TypeScript и Supabase: регистрация, вход, собственные заявки, редактирование и статусы, поиск по названию и фильтр. Интерфейс на русском, адаптивная карточная версия списка для телефона. Без подключения к Supabase приложение показывает инструкцию настройки, а не вымышленные данные.

## Быстрый запуск

Нужны Node.js 22.12+ (рекомендуется поддерживаемая LTS-версия), npm и проект Supabase. Проверки в этой среде выполняются на Node.js 25.8.2.

```powershell
npm ci
Copy-Item .env.example .env.local
# Заполните .env.local параметрами своего проекта
npm run dev
```

Откройте http://127.0.0.1:5173. Переменные Vite подставляются во время сборки: после изменения перезапустите dev-сервер или пересоберите production.

## Настройка Supabase

Проект уже создан: **LD LATTE Development / ld-latte-requests**, `https://rvfunzjedtcnrpvpsajj.supabase.co`. Подробные шаги именно для него, SQL-проверки и сценарий двух пользователей: **[SUPABASE_SETUP.md](SUPABASE_SETUP.md)**. Удалённое применение миграции пока не подтверждено: интеграция возвращает `Unknown tool`.

1. Создайте проект на https://supabase.com/dashboard. Дождитесь готовности PostgreSQL.
2. Откройте SQL Editor и выполните целиком `supabase/migrations/202611040001_requests.sql` в новой базе. Миграция транзакционная и применяется один раз; повторное применение уже существующей таблицы намеренно завершится ошибкой. Для управления миграциями CLI можно связать проект командой `supabase link --project-ref <ref>` и выполнить `supabase db push`.
3. В Authentication → Providers включите Email/password. Решите, требуется ли подтверждение email; приложение поддерживает оба режима. При включённом подтверждении после регистрации показывается сообщение о письме, доступ к заявкам появляется после подтверждения и получения сессии. Для реального корпоративного использования настройте собственный SMTP согласно ограничениям Supabase.
4. В Authentication → URL Configuration задайте Site URL своего приложения. Добавьте разрешённые Redirect URLs: `http://127.0.0.1:5173/requests` и `https://YOUR_DOMAIN/requests`. Для E2E с настоящим сервером добавляйте только используемые вами URL. Не отключайте подтверждение email только ради тестов.
5. В настройках API найдите Project URL и publishable key (или legacy anon key). Заполните `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` в `.env.local`. Это публичные браузерные параметры; безопасность обеспечивается RLS. Secret key и service_role использовать здесь нельзя.
6. Убедитесь, что таблица `public.requests` доступна через Data API и политики из миграции присутствуют. Не добавляйте политику общего доступа.

Подход к защите соответствует [документации RLS Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security), а восстановление сессии использует [события Supabase Auth](https://supabase.com/docs/reference/javascript/auth-onauthstatechange).

## Архитектура и защита

- `src/hooks/useAuth.tsx`: восстановление сессии, подписка на смену авторизации, очистка подписки.
- `src/App.tsx`: защищённые маршруты `/requests`, `/requests/new`, `/requests/:id`; `/login` — регистрация и вход. Компоненты рабочего пространства размонтируются при смене аккаунта.
- `src/components/RequestForm.tsx`: React Hook Form + Zod, обязательные поля, ограничения длины, синхронный ref-замок параллельных отправок, состояния ожидания и ошибки.
- `src/lib/requests.ts`: только явные разрешённые поля при записи; создание не передаёт владельца и статус. После сохранения список повторно читается из базы.
- SQL: UUID, FK на `auth.users`, CHECK, значения по умолчанию и индексы владельца/даты/статуса; три RLS-политики SELECT/INSERT/UPDATE; никаких прав DELETE в браузере. UPDATE имеет и USING, и WITH CHECK. Колонковые разрешения дополнительно запрещают передачу/смену владельца, начального статуса и времени. `updated_at` обновляет триггер.
- Обычный CSS вместо Tailwind: интерфейс небольшой, дополнительный инструмент сборки стилей не нужен. Поиск и фильтрация выполняются одновременно в памяти над уже разрешёнными RLS строками, без перезагрузки страницы.
- Сессия хранится Supabase SDK в браузере. Не вводите пользовательский HTML в DOM; React экранирует текст заявок. Выход локальный: другие устройства пользователя сохраняют свои сессии.

## Команды проверки

```powershell
npm run typecheck
npm run lint
npm test
npm run test:sql
npm run build
npx playwright install chromium
npm run test:e2e
```

E2E запускают свой Vite на 4173, подменяют HTTP-ответы Supabase и исполняются на 1440×1000 и 375×812. Они проверяют интерфейс и клиентскую интеграцию SDK, **не доказывают работу реального Supabase/RLS**. Не используйте тестовые URL и ключ в production. Снимки сохраняются в `test-results`. Unit-тесты проверяют валидацию, поиск/фильтр, защиту параллельной отправки, повтор после ошибки и изменение статуса.

`npm run test:sql` применяет настоящую миграцию в PostgreSQL через PGlite (WASM) и проверяет права двух ролей/пользователей, RLS, ограничения колонок, обязательные поля, начальные значения и даты. Минимальная схема `auth` создаётся самим тестом; Supabase Auth и PostgREST эта локальная проверка не заменяет.

## Реальная проверка RLS двумя пользователями

1. Примените миграцию в отдельном тестовом проекте.
2. Зарегистрируйте два различных тестовых аккаунта A и B; подтвердите их email, если подтверждение включено.
3. Скопируйте `.env.rls.example` в `.env.rls`, заполните URL, **публичный** ключ и данные A/B. Этот файл исключён из Git; не используйте рабочие пароли сотрудников.
4. Выполните `npm run test:rls`.

Скрипт обращается к настоящему Supabase API с двумя обычными пользовательскими сессиями: создаёт заявки, проверяет первоначальный статус, видимость списка, прямое чтение/обновление чужого UUID, подделку владельца при INSERT/UPDATE, анонимный доступ, ограничения полей и сохранность после повторного входа. Он завершится ненулевым кодом при нарушении. RLS часто возвращает `200 []` для скрытой строки, а не HTTP 403: скрипт проверяет отсутствие доступа и отсутствие изменённых строк.

Две тестовые записи остаются для ручного осмотра, их UUID выводятся в консоль при успехе. Удалите их через SQL Editor как владелец проекта. При неуспехе ищите их по названию `RLS test <дата>`. Скрипт не требует service_role и не даёт клиенту права удаления.

## Сценарий демонстрации

1. Откройте `/requests/new` без входа: произойдёт переход на `/login`.
2. Зарегистрируйте A, при необходимости подтвердите email, войдите. Попытайтесь отправить пустую форму.
3. Создайте заявку «Бот согласования», убедитесь в статусе «Новая». Откройте её, измените название, описание, категорию и статус.
4. Введите часть названия и выберите статус одновременно; проверьте пустую выдачу и сброс.
5. Обновите страницу; выйдите и войдите: заявка сохраняется.
6. В отдельном профиле/инкогнито войдите как B. Заявок A быть не должно, прямой URL заявки A должен показывать недоступность. Дополните проверкой `npm run test:rls`.
7. В DevTools установите ширину 375 px. Проверьте форму, список, клавиатурную навигацию и выход. При Slow network дважды нажмите сохранение: во время одного запроса отправка блокируется. При Offline должна появиться ошибка с возможностью повторить.

## Сборка и публикация

```powershell
npm run build
npm run preview
```

Папка `dist` — готовые статические файлы. Для Vercel: импортируйте Git-репозиторий, выберите Vite, команда `npm run build`, каталог `dist`, задайте обе переменные VITE в настройках. `vercel.json` содержит SPA rewrite для прямых ссылок. Для Netlify используйте те же параметры; `public/_redirects` попадёт в `dist`. Учитывайте тариф и лимиты выбранной платформы; платные услуги не подключались.

После публикации добавьте домен в Supabase Site URL и Redirect URLs, проверьте регистрацию по реальному письму, обновление `/requests/:id`, сохранение данных и изоляцию A/B. Не передавайте публикацию как готовую до этой проверки.

## Git и передача

В исходном каталоге репозитория не было; теперь локальный Git-репозиторий инициализирован. Для отправки создайте пустой репозиторий в своём GitHub и добавьте его как remote:

```powershell
git branch -M main
git remote add origin https://github.com/Maxim-Eroshchenko/ld-latte-requests.git
git push -u origin main
```

Remote `origin` уже настроен на [приватный репозиторий](https://github.com/Maxim-Eroshchenko/ld-latte-requests); повторно добавлять его не нужно. GitHub-интеграция подтвердила право push. Терминальный push пока не подтверждён: обычному Git требуется отдельный вход.

`.env*` исключены, кроме двух шаблонов. `package-lock.json` включён в репозиторий. Реальные ключи, пароли, `node_modules`, отчёты тестов и сборку добавлять не нужно. Приложение ещё не опубликовано.

Фактические результаты проверок смотрите в `AI_USAGE.md`, ограничения — в `KNOWN_ISSUES.md`.
