# Использование AI и фактические проверки

Дата: 4 ноября 2026 года. Инструмент: Codex. Исходные требования: пользовательский технический запрос и файл `D:/Desktop/Задача.txt` как описание тестового задания.

## Что сделал Codex

Спроектировал и написал приложение React/TypeScript/Vite, интеграцию Supabase Auth и Data API, защищённые маршруты, формы, поиск и фильтр, русский адаптивный интерфейс, SQL-миграцию с RLS и колонковыми правами. Добавил unit/component-тесты, Playwright E2E, локальную проверку PostgreSQL и отдельный скрипт для проверки настоящего Supabase двумя пользователями. Подготовил README, инструкции публикации, конфигурацию SPA rewrite для Vercel/Netlify, шаблоны переменных и этот отчёт. Изображения и генеративные медиа не использовались. Субагенты не использовались.

## Решения

- Supabase — единственный источник реальных аккаунтов и данных. В production нет локальной имитации хранилища. Без конфигурации показывается экран подключения.
- Владелец, UUID, начальный статус и даты назначаются БД. RLS действует независимо от UI; права INSERT/UPDATE ограничены колонками.
- При восстановлении сессии учитываются события SDK, чтобы более старый результат `getSession` не заменял актуальную сессию. При смене пользователя защищённое дерево размонтируется.
- Сохранение защищено синхронным ref-замком и отключением кнопки/полей. Ошибка освобождает замок; после успеха список читается заново.
- React Hook Form и Zod для форм. Простой CSS вместо Tailwind, Lucide для иконок. Поиск на клиенте по собственным разрешённым строкам.
- PGlite позволяет выполнить настоящую SQL-миграцию и PostgreSQL RLS локально, не заявляя о подключении к Supabase. Его минимальная `auth`-схема — тестовый стенд.
- Точная установка воспроизводится через `package-lock.json` и `npm ci`. Для исправления транзитивной уязвимости задан override minimatch 11. После него линтер проверен повторно.

E2E используют реальный Supabase JS SDK в браузере, но HTTP-ответы подменяются тестом. Проверены защищённый маршрут, регистрация с требованием подтверждения, вход/выход, создание и редактирование, смена статуса, совместный поиск/фильтр и сброс, повторный вход и обновление страницы, сетевой сбой, двойной клик, отсутствие горизонтального переполнения. Локальный SQL-тест проверяет миграцию, значения по умолчанию, A/B-изоляцию SELECT и UPDATE, прямой запрос чужого UUID, подделку владельца, недопустимые поля/категории/статусы, пробелы и табуляции вместо текста, защищённые даты, обновление `updated_at`, запрет анонимного чтения и DELETE. После команды пользователя продолжить сдачу инициализирован локальный Git-репозиторий. Проверен индекс: в нём только два env-шаблона, `node_modules`, `dist` и `test-results` не отслеживаются, `git diff --cached --check` ошибок не обнаружил. ## Проблемы и исправления

1. Песочница не разрешала DNS к npm и localhost. Установка, браузерные прогоны и обновлённый Vitest потребовали разрешённого запуска вне песочницы. Результаты не подменялись пропуском проверок.
2. Первый npm-аудит сообщил 14 уязвимостей (12 moderate, 2 critical) в инструментах разработки. Обновлены ESLint/TypeScript ESLint/Vitest, minimatch закреплён на исправленной ветке. Попытка Vitest latest выбрала 5.1.0 с неподходящим диапазоном Node 25; установлен совместимый Vitest 4.1.12. Итоговый отчёт — 0 уязвимостей.
3. Линтер обнаружил `let` у неизменяемой ссылки тестового массива; заменено на `const`.
4. Для первого запуска Playwright не было бинарника браузера. Chromium установлен, тесты повторены.
5. Два E2E-селектора были неоднозначными: «Новая» встречалась в option и бейдже, роль status — у уведомления и загрузки. Селекторы уточнены до бейджа и текста уведомления; полный прогон затем прошёл.
6. При проверке SQL усилена проверка обязательных строк: запрещены значения только из табуляций/переносов строк, а не только обычных пробелов.
7. Вспомогательная попытка редактирования через `node -e` не прошла из-за кавычек PowerShell; изменений не произвела. Изменения внесены патчем, исходники отформатированы Prettier.
8. Rollup при сборке предупреждает об аннотациях PURE в стороннем Zod. Сборка завершается успешно; исходники сторонней библиотеки не изменялись.

## Участие пользователя и оставшиеся действия

Для сетевых установок и браузерных тестов использовался механизм разрешений среды. Реальные ключи, пароли и платные сервисы не добавлялись. Пользователь создал Supabase-проект **LD LATTE Development / ld-latte-requests** с ref `rvfunzjedtcnrpvpsajj` и приватный GitHub-репозиторий. Интеграция GitHub после выдачи доступа подтвердила право push; обычный Git не авторизован.

Для конкретного Supabase-проекта повторно вызваны `get_project_url`, `list_tables`, `get_publishable_keys`; каждый вернул `Mcp error: -32001: Unknown tool`. Удалённая схема не читалась, миграция не применялась. Подготовлены `SUPABASE_SETUP.md`, сценарий SQL Editor `supabase/tests/verify_requests.sql` с двумя настоящими Auth UUID и откатом, URL в env-шаблонах и локальная `.env.local` с пустым ключом (только если файла ранее не было). Сценарий SQL Editor выполнен в локальном PostgreSQL/PGlite, включая проверку неизменности количества записей после rollback. После изменений прошли 22 локальные SQL-проверки, линтер и TypeScript. Облачный API-прогон не запускался.

Актуальное состояние: пользователь настроил таблицу и политики, публичный ключ и два аккаунта. Миграция повторно не запускалась. В реальном браузере проверены вход, создание, редактирование всех полей, обновление страницы, поиск/фильтр, отсутствие заявки A у B и отказ B по прямому UUID. `npm run test:rls` с настоящими A/B завершился с PASS и кодом 0. Две помеченные API-тестовые заявки оставлены для осмотра. Пароли введены пользователем только в игнорируемый `.env.rls`, в чат не выводились. Эти результаты заменяют прежние статусы в историческом описании выше. Для публикации используется существующая статическая React/Vite-сборка и manifest Sites; архитектура не менялась. Настройка Supabase production Site URL/Redirect URLs поручена пользователю.
